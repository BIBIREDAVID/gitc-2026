# GITC 2026 Registration Site

## Project

Registration site for **GITC — Get Into Tech Conference 2.0**, hosted at LASU (Lagos State University), in partnership with Zenith Bank. Flyer: `flyer-original.png` — dark, neon blue-violet to magenta gradient, cyan accents, wide heavy headings, monospace labels. Match this visual language throughout the site.

A free, single-event registration site:
- Visitors see the flyer, fill a form, get a QR ticket.
- Staff scan tickets at the door.
- Organisers manage everything from an admin portal.

## Stack

- Plain JavaScript (JSX, no TypeScript)
- React + Vite
- react-router-dom
- **Supabase**: Postgres (+ Row Level Security), Auth, Edge Functions (Deno) — in `/supabase`
- Deployed on Vercel

> **Migrated from Firebase to Supabase on 2026-10-04.** The original build
> (everything in "Status" below the migration note) used Firebase
> (Firestore/Auth/Cloud Functions) throughout — kept here for historical
> context since the *shape* of every feature carried over unchanged, but
> every Firebase-specific implementation detail (Firestore collections,
> `firestore.rules`, `functions/src/*.js`, `firebase.js`) was replaced. The
> reason: Cloud Functions requires Firebase's paid Blaze plan with no free
> alternative, and billing wasn't an option. Supabase's free tier includes
> Edge Functions with no card required. See "Supabase migration" near the
> bottom for the current architecture — that section is the accurate one for
> anything backend-related; the Firebase-era Status entries below describe
> code that no longer exists.

## Rules

1. **Mobile first.** Design at 375px wide. Most users arrive from WhatsApp links on phones with weak connections.
2. **No payments.** The event is free.
3. **No direct writes.** Visitors never write to the database directly. All registration writes go through Edge Functions, using the service role, inside a single-transaction Postgres function.
4. **TBA-safe.** Event date/time, capacity, and the email sender are all TBA. The site must work while:
   - date is empty
   - capacity is empty (meaning unlimited)
   - email is switched off
5. **No secrets in code.** Vite vars in `.env.local` (prefix `VITE_`). Server keys as Supabase Edge Function secrets / env vars, never prefixed `VITE_`. Keep `.env.example` with every variable name and no values.
6. **Roles via claims.** Supabase Auth `app_metadata`: `admin` and `staff` (writable only via the service role / Admin API — the Supabase equivalent of Firebase custom claims).
7. **Minimal personal data.** Public-readable data must never contain email or phone — enforced by `get_ticket_by_code()` only ever selecting `full_name`/`pickup`/`checked_in`.
8. **Centralized form config.** All form options live in one file: `src/config/formOptions.js`.

- **Bundle / code-splitting**: every route except `/` is now `React.lazy()` (previously only `/admin` and `/checkin` were). `src/lib/firebase.js` no longer imports `firebase/auth` or `firebase/functions` at all — those live in two new files, `src/lib/authInstance.js` and `src/lib/functionsInstance.js`, each exporting a `getXInstance()` that lazily `import()`s the SDK and caches the instance. - **Security review**:
  - **No personal data in public documents** — confirmed by the E2E test itself (`assert.equal(ticket.email, undefined)` / `whatsapp` likewise) and by `tests/firestore.rules.test.js`: `tickets/{code}` only ever held `fullName`/`pickup`/`checkedIn` (enforced by `functions/src/register.js` only ever writing those three fields to it); `settings`/`stats` are aggregate-only.

  - **Callable functions reject malformed input** — re-verified, and hardened further this pass: `functions/src/validation.js` now caps every free-text field length (name ≤100, other free-text ≤200, raw email/phone ≤100 chars before normalisation — all generous, well above anything a real attendee would type) and the `interests` array (≤13, de-duplicated) — previously an attacker could send an arbitrarily large string or an array with thousands of duplicate entries and it would validate, bloating Firestore document size/cost for no legitimate reason. `functions/src/checkIn.js`'s `normalizeCode` now also caps scanned-code length (≤500 chars). Confirmed via direct unit calls that oversized/duplicated input is now rejected or de-duplicated as expected.
  - **Risks found, not fixed this pass** (listed, not silently patched over):
    1. `register` has **no rate limiting** (unlike `findTicket`, which has a 10/IP/hour limit). Deliberately not added one: this is a free walk-up event where many attendees will register from the same campus WiFi NAT/shared IP, so a naive per-IP limit risks blocking legitimate concurrent sign-ups during a rush. The honeypot + email/phone dedupe transaction are the current abuse mitigations. If spam becomes a real problem, the correct fix is **Firebase App Check** (attests the request came from the real web app, not a script) rather than IP throttling — out of scope for this pass.
    2. No CAPTCHA/App Check on `register` or `findTicket` at all — same App Check recommendation applies.
    3. `functions/src/validation.js` (server) and `src/lib/validation.js` (client) are hand-kept-in-sync duplicates (documented in both files already) — the new length caps were only added server-side this pass. A user pasting a 500-character name gets a generic "invalid" error with no inline field feedback, since the client doesn't know about the cap. ## Supabase migration (2026-10-04)

Firebase's Cloud Functions requires the Blaze (paid) plan with no free path — discovered during deployment, after the whole app was already built on Firebase. Billing wasn't an option, so the backend moved to Supabase (Postgres + Edge Functions), which has a genuinely free tier including Edge Functions. Every *feature* carries over unchanged; only the implementation did. No local emulator was available for this migration (Supabase's CLI needs Docker, not installed in this environment), so everything was built against the real hosted project directly.

### Schema (`supabase/migrations/`)

- `settings` / `stats` — single-row tables (`id = 1`), replacing the Firestore `settings/event` and `stats/summary` singleton docs.
- `registrations` — one row per attendee. `email` and `whatsapp` are plain Postgres `UNIQUE` columns — this **replaces Firestore's whole `uniques/e_*` / `uniques/p_*` collection**; duplicate detection is now just a unique-constraint violation caught in the registration function, no separate dedupe documents needed.
- `rate_limits` — same role as Firestore's `rateLimits/`, for `find-ticket`'s 10/IP/hour limit.
- **No `tickets` table.** Firestore's rules could express "get by exact doc id, but never list the collection" directly; PostgREST's table API can't — granting `SELECT` on any table/view lets a client pass an arbitrary filter and enumerate every row. The equivalent is `public.get_ticket_by_code(p_code text)`, a `SECURITY DEFINER` SQL function that takes the code as a required parameter and returns at most one row (`full_name`, `pickup`, `checked_in` only — rule 7). There's no way to call it without already knowing a real code, which *is* "get only, no list."
- `register_attendee()`, `check_in()`, `admin_delete_registration()` — `SECURITY DEFINER` PL/pgSQL functions doing the atomic part of what the Firebase Cloud Functions did in a Firestore transaction (Postgres functions are single-transaction by default, so this needed no extra syntax). Each is `REVOKE ALL FROM public` — callable only via the service role, from inside the matching Edge Function.

### Row Level Security (replaces `firestore.rules`)

- `settings`: `SELECT` for everyone, `UPDATE` only if `(auth.jwt() -> 'app_metadata' ->> 'admin')::boolean is true`.
- `registrations` / `stats`: `SELECT` only for staff or admin (same JWT check, OR'd). **No insert/update/delete policy for any role at all** — all real writes go through the `SECURITY DEFINER` functions above, which bypass RLS entirely by design (the Postgres equivalent of "writes only via the Admin SDK").
- `rate_limits`: no policies at all — closed entirely, same as Firestore's `rateLimits` rule.
- Verified with `tests/rls.test.js` (`npm run test:rls`) — ports every case from the old `firestore.rules.test.js`: public can't read `registrations`/`stats`, public can't write anywhere, public can `get_ticket_by_code()` by exact code but has no way to list, staff can read `registrations` but not write `settings`, admin can write `settings`.

### Edge Functions (`supabase/functions/`, replaces `functions/src/*.js`)

Deno/TypeScript, one function per Firebase callable, same names minus camelCase (`checkInManual` → `check-in-manual`, etc). `_shared/validation.ts` is a line-for-line TypeScript port of `functions/src/validation.js`'s rules (length caps, interest-array cap/de-dupe, the exact same WhatsApp-normalisation regex) — now the third copy of this logic alongside `src/lib/validation.js`, kept in sync by hand same as before.

- `register` — honeypot check, then `validateAndNormalize()`, then one call to `register_attendee()`. No auth required (public).
- `find-ticket` — rate limit check/increment against `rate_limits`, then a direct `registrations` select by email+whatsapp (service role, bypasses RLS) for the matching `ticket_code`. No auth required (public).
- `check-in` / `check-in-manual` — `_shared/auth.ts`'s `requireUser()` decodes the caller's JWT via `supabase.auth.getUser(token)` and checks `app_metadata.staff`/`.admin` before calling `check_in()`.
- `admin-delete-registration` — same auth check, admin-only, calls `admin_delete_registration()`.
- `send-ticket-email` — sends via **EmailJS** (`api.emailjs.com/api/v1.0/email/send`, plain REST call — EmailJS's own SDK is browser-only and doesn't run in Deno). No-ops unless `settings.email_enabled` is true AND all four `EMAILJS_SERVICE_ID`/`EMAILJS_TEMPLATE_ID`/`EMAILJS_PUBLIC_KEY`/`EMAILJS_PRIVATE_KEY` secrets are set (rule 4 — TBA-safe while email stays off). `EMAILJS_PRIVATE_KEY` (the EmailJS account's "Private Key") is required because EmailJS's REST API rejects non-browser-origin calls without it. Template gets `to_email`/`to_name`/`ticket_code`/`ticket_url` (built from the `SITE_URL` secret + `/ticket/<code>`). Firestore's `onCreate` trigger has no exact Postgres equivalent without extra extensions; this still needs a **Database Webhook** configured manually in the dashboard (Database → Webhooks → INSERT on `registrations` → this function) — deliberately not done as a SQL migration trigger, since Supabase's dashboard-created webhooks keep the service-role auth header in Vault, while a hand-written SQL trigger would have to embed it as a literal argument (a secret committed to the repo). Not yet configured — see "Still outstanding" below.

### Front end

- `src/lib/firebase.js` → `src/lib/supabase.js`: one `createClient()`, no lazy-loading gymnastics needed — `@supabase/supabase-js` is a single lightweight package (no Firestore/Auth/Functions SDK split to fight), which is *why* the main bundle shrank by ~60%, not because of anything deliberately optimised this time.
- `onSnapshot` real-time listeners → Supabase Realtime (`supabase.channel(...).on('postgres_changes', ...)`), used in `useEventSettings.js`, admin's `useRegistrations.js` and `SettingsTab.jsx`, and the check-in counter — all three tables were added to the `supabase_realtime` publication in a migration for this to work at all.
- `httpsCallable()` → `supabase.functions.invoke()` throughout (`src/lib/api.js`, `RegistrationsTab.jsx`'s delete, `CheckInApp.jsx`'s scan/manual check-in).
- Firebase Auth (`getIdTokenResult().claims`) → Supabase Auth (`session.user.app_metadata`) in `useAdminAuth.js`/`useStaffAuth.js` — same `'checking' | 'signed-out' | 'denied' | 'authed'` shape, same deny-and-sign-out-if-not-admin/staff behaviour.
- `Ticket.jsx` now calls the `get_ticket_by_code` RPC instead of a direct Firestore `getDoc`.

### Scripts

- `scripts/seed.js`, `scripts/setRole.js`, `scripts/seed-admin.js`, `scripts/seed-sample-data.js` — all rewritten for `@supabase/supabase-js` + `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` (same safety properties as before: `seed.js` is still only-if-missing, `setRole.js` still never touches a password, still only ever reads credentials from env vars).
- `firebase-admin`, `firebase`, `firebase-tools`, `@firebase/rules-unit-testing` removed from `package.json`. `functions/`, `firebase.json`, `.firebaserc`, `firestore.rules`, `firestore.indexes.json`, and the old `tests/firestore.rules.test.js` deleted.
